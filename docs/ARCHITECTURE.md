# 技術背景 / 調べた設計メモ

実務で必要になるクラウド設計を調べて、この構成にした理由・代替案・限界をまとめた設計メモ。
**ヘルスチェック分離・キャッシュ戦略・冗長化・IaC などは、実務経験ではなく学習として整理したもの**で、
実際に構築・運用しているのはボット本体(単一 EC2)の部分のみ。
図は [`architecture.drawio`](architecture.drawio)、README にも mermaid 版あり。

---

## 0. 前提と目的

- 監視対象は、通貨の自動売買で **4 戦略統合のボット(別管理)を EC2 上で数ヶ月以上稼働**させているシステム。
  1 時間ごとに全 12 通貨ペアをチェックし発注する
- 運用中に「稼働しているつもりで止まっていた」「シグナルの過半数が証拠金不足で失注していた」
  「プロセスが二重起動して実質 2 倍のリスクを取っていた」という問題に**事後で**気づいた
- 目的は 2 つ:
  1. **運用**: これらを早期に気づける 1 画面を用意する(実用)
  2. **学習/ポートフォリオ**: 実務で必要になる AWS の設計パターン(冗長化・水平スケール・
     キャッシュ戦略・ヘルスチェック設計・IaC 化)を、実在するシステムを題材に調べて整理する
     (※構築・運用しているのはボット本体の単一 EC2 のみ。冗長化構成は図と設計メモのみ)

## 1. 設計判断

### 1-0. ダッシュボードの主目的は「資産推移の可視化」ではなく「バックテスト整合性の検証」

- **背景**: 資産推移や勝率だけを見ていても「バックテスト前提から外れた動き」に気づけない。
  実際に 運用ログの分析で、資産曲線は右肩上がりのまま
  ①失注が過半数、②プロセス二重起動、③`max_positions` の食い違い、④手法別シグナル比率のドリフト
  が起きていた
- **採用**: バックテストの前提を `app/baseline.py` にコード化し(risk% / 優先順位 / 期待シグナル比率 /
  `max_positions` / スリッページ / CAGR・MaxDD)、`app/reconciliation.py` が実データと突き合わせて
  各項目を `ok / warn / fail / info` で返す。ダッシュボード最上部にこの結果を出す
- **チェック項目**(それぞれ「何を疑うか」を note で返す):
  1. **バックテスト再現 ①シグナル単位** — OHLC を戦略ロジックに通し entry シグナルを再現、
     実 signal_events と 1 件ずつ突合(MATCHED / MISSING / EXTRA / MISMATCH)。詳細は 1-0b
  2. **バックテスト再現 ②トレード・損益単位** — エグジットも再現した「バックテストなら成立した
     トレード」と実 trades を突合。カバレッジ・勝敗一致・平均R・決済理由。詳細は 1-0b
  3. シグナル→約定の実行率(全約定前提からの乖離)
  4. 手法別シグナル比率のドリフト(バックテスト件数比 ±15pt)
  5. 二重発注 / 二重稼働(同一サイクル・同一ペア×手法の EXECUTED が複数)
  6. 1 ペア 1 ポジション制約(建玉期間の重なり)
  7. 同時建玉数の上限(コードの `max_positions=6` 到達 = 方針「上限なし」との不一致)
  8. 手法別リスク%(k 値のズレ)
  9. 成績 vs バックテスト(判定せず並記。運用日数を明示し、短期間は年率換算しない)

### 1-0b. トレード単位の照合は「参照実装 vs ログ」— exact parity への段階

- **やり方**: `backtest/replay.py` が OHLC(`fx_cache/*.csv` = バックテストに使った HistData.com の
  1時間足。GMO の実フィードではない点に注意 → PARITY.md、または同梱の `sample_ohlc.csv`)を
  `backtest/strategies.py` に通し、ウォークフォワードで
  「バックテストなら出したシグナル」を再現。実運用シグナルと `(pair, strategy)` 一致 + 時刻 ±90分 で
  グリーディにマッチングし、差分を `parity_runs` に保存。ダッシュボードは最新の run を表示する
- **②トレード単位**: `backtest/exits.py` が期待シグナルを起点に SL/TP/トレールを OHLC で 1 本ずつ
  進めて手仕舞いし、「バックテストなら成立したトレード(entry/exit/R/決済理由)」を作る。
  実 `trades` と (pair, strategy, entry±2h) でマッチし、**カバレッジ**(取れた割合。低い=証拠金不足で
  見送り)と**勝敗一致率**(取れた分が想定どおりの結果か)を分けて出す。平均 R sim vs 実で
  「バックテストの取り分をどれだけ実現できているか」も見える。エグジットは近似モデル(PARITY.md 限界3)
- **オフラインジョブにした理由**: 指標計算が重い(数ヶ月 × 12ペア)。`ingest` と同じく
  「別プロセスで走らせて結果を DB に置き、Web は読むだけ」に寄せた。Web リクエストごとに回さない
- **限界(意図的なスコープ)**: `strategies.py` は監視対象ボットのシグナル関数
  そのものではなく、確定パラメータからの**再実装**。本番コードは yfinance 取得と GMO API 呼び出しに密結合しているため。
  厳密一致には、シグナル判定を純粋関数として共有モジュール化し、ボットとリプレイの両方が import
  する必要がある(→ `docs/PARITY.md` に移行手順)。「差分に参照実装のズレが混じる」ことを承知の上で、
  まず粗い照合を常時回して乖離の兆候を掴む、という段階的アプローチ
- **面接での言い方**: 「理想は本番のシグナル関数をそのまま呼ぶこと。現状はコード分離が済んでいないので
  仕様から起こした参照実装で代替し、そのことを README に明記しています。exact parity には
  `strategy_core.py` への切り出しが必要で、それが次の一手です」
- **代替案と不採用理由**:
  - Grafana / CloudWatch Dashboards で数値を並べる → 閾値アラートは作れるが「バックテストの
    前提定義」をアプリのドメイン知識として持てない。手法優先順位や 1 ペア 1 ポジションのような
    ロジック制約の検証は自前コードのほうが素直
  - バックテスト値を画面に直書き → `baseline.py` に集約してテスト可能にした
- **効いてくる場面**: 面接で「何のためのダッシュボードか」を一言で言える
  (「実運用がバックテストどおり動いているかを検証する」)。単なる損益ビューアと差別化できる

### 1-1. ボット本体に手を入れず「ログ起点」で疎結合にする

- **背景**: 監視のためにボット(別管理)を改修すると、監視側のバグが売買を止めるリスクがある。
  実際に systemd 化のとき `StandardOutput=append` の設定ミスでログが二重書き込みになった前科がある
  (EC2 障害復旧の記録 8-2)
- **採用**: ボットが既に吐いている `fxbot.log` を**唯一の入力**にする。ボットは無改修。
  取り込み側(`ingest/`)はバイトオフセットを `.ingest_state.json` に記録し、追記分だけを冪等に処理する
- **代替案と不採用理由**:
  - ボットから DB へ直接 INSERT させる → ボット改修が必要・結合が強くなる・DB 障害がボットに波及
  - CloudWatch Logs エージェントで転送 → 将来的にはあり。初手としては依存先が増える
- **トレードオフ**: ログ書式が変わると取り込みが壊れる。→ パーサを純粋関数に切り出し
  (`ingest/parser.py`)、`tests/test_parser.py` で書式を固定。書式変更時はテストを直してから対応

### 1-2. 集計は SQL ではなく pandas

- **背景**: ローカルは SQLite(ゼロ設定)、本番は RDS/PostgreSQL。日付グルーピングや
  ウィンドウ関数は方言差が出る
- **採用**: 生の行を DataFrame に読み出し、勝率・PF・最大 DD・手法別/ペア別・シグナル実行率を
  Python 側で計算(`app/aggregations.py`)。関数は `engine` を引数に取れるようにして
  一時 SQLite でユニットテスト可能にした(`tests/test_aggregations.py`)
- **代替案と不採用理由**:
  - SQL 集計 + マテリアライズドビュー → 高速だが方言依存・テストが重い。データ量(hourly bot、
    4 ヶ月で数千行)では pandas で十分速い(数十〜数百 ms)
- **効いてくる場面**: 「勝率 = wins/len」「PF = gross_profit/gross_loss」「実行率 =
  EXECUTED/(EXECUTED+MARGIN_INSUFFICIENT)」といった定義をテストで固定できる

### 1-3. Redis(ElastiCache)は必須依存にしない

- **背景**: 集計は数十〜数百 ms かかる。60 秒ポーリングのダッシュボードなので TTL キャッシュがよく効く。
  一方、ローカル体験を Redis 必須にはしたくないし、キャッシュ障害でダッシュボードを落としたくない
- **採用**: `app/cache.py` で「Redis があれば使う、無ければプロセス内 TTL 辞書」に**透過フォールバック**。
  `REDIS_URL` 未設定・起動時 ping 失敗・実行時例外のいずれでもローカルに切り替わる。
  現在の backend(`redis` / `in-process`)を画面に表示して、どちらで動いているか分かるようにした
- **キャッシュ無効化**: 取り込み(`ingest_once`)完了時に `cache.clear()` を呼び、古い集計を残さない
- **限界(正直に)**: TTL 失効の瞬間に複数リクエストが来ると全員が再計算する(キャッシュスタンピード)。
  今の負荷では問題ないが、規模が出るなら「ロック + シングルフライト」か「非同期で事前計算」が必要
- **代替案**: メモリキャッシュのみ(複数インスタンスでキャッシュがばらつく)/ CDN キャッシュ
  (認証付き動的画面には不向き)

### 1-4. ヘルスチェックを `/healthz` と `/readyz` に分ける

- **`/healthz`(liveness)**: プロセスが生きていれば 200。**ALB / ECS のヘルスチェックはこれ**を使う
- **`/readyz`(readiness)**: `SELECT 1` で DB 到達性を確認。落ちていれば 503
- **なぜ分けるか**: DB が一時的に落ちたとき、
  - readiness を LB チェックに使うと**全インスタンスが同時に外れて全断**する
  - liveness をチェックに使えば、インスタンスは LB に残り、DB 回復で自然復帰する。
    「アプリの再起動で直る問題」と「依存先の問題」を切り分けられる
- Kubernetes の liveness/readiness probe と同じ考え方。ALB 単体だと 1 種類しか設定できないので
  **`/healthz` を選ぶ**のが定石

### 1-5. 冗長化(ALB + Auto Scaling + ElastiCache)は未構築の検討

- 個人のボット 1 台の監視画面に ALB・水平スケール・マネージド Redis は**実運用としては過剰**
- **なぜ図にしたか**: 事業会社/SIer の実務で出てくる「2 AZ 冗長」「ローリングデプロイ」
  「ヘルスチェック設計」「ステートレス設計」がどういうものかを調べて整理するため。**実際には構築していない**
- **運用判断**: ボット EC2 は**単一構成のまま**が正しい。1 台停止 ≒ 最悪 1 サイクル
  (1 時間)のシグナル欠損で、Elastic IP + systemd + `ec2:recover` で数分〜十数分で戻る。
  ALB を足すコスト(月 ¥2,500〜)に見合わない

### 1-6. ステートレス設計(スケールアウトの前提)

- アプリはリクエスト間の状態をプロセスに持たない。状態は RDS(永続)と Redis(キャッシュ)にのみ置く
- だから Auto Scaling で台数を増減しても、どのインスタンスに当たっても同じ結果になる
- プロセス内キャッシュ(1-3 のフォールバック)は**インスタンスごとにばらつく**が、
  TTL 60 秒・読み取り専用の集計なので実害がない範囲。厳密な一貫性が要るデータではない

### 1-7. マイグレーションは今は `create_all`、本番運用なら Alembic

- デモ/SQLite では起動時に `Base.metadata.create_all` でテーブルを作る(`app/db.py: init_db`)
- 継続運用してスキーマを育てるなら Alembic を入れてバージョン管理する。今は「初版」として割り切り

## 2. 各コンポーネントの役割

| コンポーネント | 役割 | 技術的ポイント |
|---|---|---|
| **Route 53** | ドメイン → ALB の名前解決 | エイリアスレコードで ALB を指す(A レコード直書きより ALB の IP 変動に強い) |
| **ACM** | TLS 証明書 | ALB にアタッチ。パブリック証明書は所有ドメインの DNS 検証が必要。無料・自動更新 |
| **ALB** | L7 ロードバランサ / TLS 終端 / ヘルスチェック | ターゲットグループのヘルスチェックパス `/healthz`。80→443 リダイレクトをリスナールールで |
| **Auto Scaling (EC2×2)** | アプリの冗長化・水平スケール | 2 AZ にまたがせて AZ 障害耐性。起動テンプレートで User data から `docker` 起動 |
| **EC2 上の FastAPI (uvicorn)** | ダッシュボード本体 | ステートレス。IAM インスタンスプロファイルで CloudWatch を read |
| **RDS for PostgreSQL** | 構造化した trades / signal_events / equity_snapshots / heartbeats | `Publicly accessible=No`、SG でアプリ SG からのみ。バックアップ保持 1 日〜 |
| **ElastiCache for Redis** | 集計結果の TTL キャッシュ | 任意依存。SG で絞るのが唯一の防御(認証を張らない構成なら特に) |
| **CloudWatch Alarms** | 監視ボット EC2 の物理ホスト障害検知 | ダッシュボードは `describe_alarms` で**既存**アラームの状態を read するだけ |
| **ingest ワーカー** | `fxbot.log` → RDS | ボット EC2 に同居。systemd サービス化(`Restart=always`)。バイトオフセットで冪等 |

### CloudWatch まわりの技術背景(既存資産の再利用)

- `StatusCheckFailed_System`(物理ホスト側)と `StatusCheckFailed_Instance`(OS 側)は別メトリクス。
  **Auto Recovery(`ec2:recover`)は `_System` を監視するアラームにしか付けられない**
- 既存の統合メトリクス `StatusCheckFailed` のアラームは SNS 通知専用だったため、
  `_System` 専用アラームを別途作って `ec2:recover` + SNS の両方をアクションに設定してある
- ダッシュボードはこの状態を可視化するだけで、アラーム自体は作らない(責務分離)
- 詳細: EC2 障害復旧の記録

## 3. データモデル

```
bot_heartbeats    : メインチェック 1 サイクル = 1 行。死活監視の元データ(cycle_id ユニーク)
equity_snapshots  : 口座状況(有効証拠金・維持率・建玉数)のスナップショット(ts ユニーク)
signal_events     : シグナル検出 / 発注結果 / 決済の生イベント。発注失敗も 1 行として残す
                    line_hash(raw 行の SHA1)で冪等性を担保
trades            : signal_events から導出。order(EXECUTED) で open、exit(CLOSED) で close
                    position_id ユニーク
```

- **なぜ `signal_events` と `trades` を分けるか**: 「シグナルは出たが証拠金不足で発注できなかった」
  という**失注**を残したいから。`trades` だけだと成功した取引しか見えず、失注に気づけない
- **冪等キーの使い分け**: heartbeat=`cycle_id`、equity=`ts`、signal_event=`line_hash`、trade=`position_id`。
  同じログを 2 回流しても重複行を作らない

## 4. セキュリティ設計

| 対象 | 方針 |
|---|---|
| 認証情報 | `.env` は Git 除外(`.gitignore`)+ Push protection。本番は SSM Parameter Store か各サーバー手配置 |
| AWS 権限 | アプリは **IAM インスタンスプロファイル**で `cloudwatch:DescribeAlarms` の read のみ。アクセスキーをコード/ENV に置かない |
| RDS | `Publicly accessible=No`。SG で「アプリの SG」からのみ 5432 |
| ElastiCache | SG で「アプリの SG」からのみ 6379。到達経路の制限が主防御 |
| ALB | 443 のみ公開、80 は 443 へリダイレクト。TLS 終端は ACM |
| ログ内個人情報 | 売買ボットのログには顧客情報は無い(自分の口座のみ)。将来ログ源が増えるならマスキングを検討 |

## 6. 調べた論点メモ(Q&A 形式)

> 設計を検討する中で自分用に整理した論点。**ヘルスチェック分離やスケール限界などは
> 実務でやった経験ではなく、調べてまとめた理解**。ボット本体の運用・障害対応は実体験。

- **Q. なぜ個人の bot にこんな大げさな構成を?**
  A. 実務で必要になる冗長化・ヘルスチェック・IaC がどういうものか、実データが流れる対象で調べたかった。
  bot 自体は単一構成が正しく、冗長化構成は未構築のまま。
- **Q. Docker やコンテナは?**
  A. ローカルは venv + uvicorn + SQLite の 1 プロセスで動く。docker-compose も用意しているが、
  ボット本体は素の EC2 上の systemd 常駐で、コンテナは使っていない。
- **Q. Redis を消したらどうなる?**
  A. `REDIS_URL` を外すだけでプロセス内キャッシュにフォールバックして動きます。画面に backend を表示しています。
- **Q. ログ書式が変わったら?**
  A. 取り込みが影響範囲。パーサを純粋関数に切り出してテストで固定しているので、テストを直してから対応します。
  売買ロジックには一切影響しません。
- **Q. `/healthz` と `/readyz` を分けた意図は?**
  A. DB 一時障害のとき readiness を LB チェックに使うと全インスタンスが同時に外れて全断します。
  liveness をチェックに使えばインスタンスは残り、DB 回復で自然復帰します。
- **Q. この構成のスケール上のボトルネックは?**
  A. まず RDS。読み取り主体なのでリードレプリカ、次に集計の事前計算(キャッシュスタンピード対策)です。
- **Q. 何のためのダッシュボード? 資産推移なら証券会社の画面で見られるのでは。**
  A. そのとおりで、これは損益ビューアではありません。中心機能は「実運用がバックテストの前提どおりに
  取引できているか」を機械的に検証することです。バックテスト前提を `baseline.py` にコード化し、
  失注率・手法別シグナル比率のドリフト・二重発注・1 ペア 1 ポジション違反・`max_positions` 到達を
  突き合わせて OK/要確認/NG で出します。実際にこれらは資産曲線が右肩上がりのまま起きていました。
