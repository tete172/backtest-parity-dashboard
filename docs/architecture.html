現状 / As-Is

現行構成 — 監視対象そのもの

このダッシュボードが監視する、実際に数ヶ月以上稼働しているボットの構成。 価格フィードは 3 系統(シグナル判定 = Yahoo Finance、約定 = 取引所 API、バックテスト = ヒストリカルデータ)。

  • 3 フィードの違いがバックテスト照合の残差要因になる(詳細は docs/PARITY.md)。

導入後 / To-Be・未構築

ダッシュボード導入後の想定構成

⚠️ これは設計段階の想定図で、実際には構築していない。 今動いているのはローカル起動(SQLite・プロセス内キャッシュ)のみ。 ボット本体には手を入れず、既存の fxbot.log を唯一の入力にする疎結合設計。 集計は pandas、キャッシュ(Redis)は任意依存、ヘルスチェックは /healthz と /readyz を分離 ── というアプリ側の設計はこのリポジトリに実装済みで、 RDS / ALB / Auto Scaling / ElastiCache は未構築のまま。

本番運用

ログ取り込みトポロジ — 手動 SCP なしで自動化する

手動 SCP は「ローカル初回に parser の正規表現が実ログ書式と合うか確認する」ためだけ。 本番は次の A / B / C いずれかで自動化する。取り込みはバイトオフセットを .ingest_state.json に記録するので、何度流しても重複しない(冪等)。

  • A: fxbot.log がただのローカルファイルになる。ingest --follow を systemd サービスで回すだけ。転送の仕組みが一切要らない。
  • B: DATABASE_URL を RDS に向ける。ログは EC2 から出ず、構造化した行だけが DB 接続で流れる(To-Be 図がこれ)。
  • C: ingest に S3 / CloudWatch Logs 読み込みの小改修が必要。多数のボットを 1 つのダッシュボードで見るとき向け。
つなぎ運用なら A が最小コスト。ローカルでの初回 SCP は「parser が実ログ書式に合うか」を確認する 1 回だけと割り切ってよい。
